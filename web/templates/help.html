How it works

Crossprint rewrites a sliced .3mf project so a different printer's slicer will open it as its own. It does not re-slice, and it does not touch your models.

The one-minute version

  1. Drop in a .3mf project saved by Bambu Studio or Snapmaker Orca. The source printer is read from the file — there is nothing to pick.
  2. Choose a target printer. Any direction works, including Bambu → Bambu.
  3. Read the change list. Every rewrite, drop and substitution is shown before you download, grouped by what it touched.
  4. Download, open in the target's slicer, and re-slice. That last step is not optional — see below.

Why you always have to re-slice

A saved project holds two very different things: the recipe (models, colours, painting, print settings) and the result (toolpaths and G-code for one specific machine). Toolpaths are computed for a particular bed, hotend, kinematics and filament routing, and no amount of rewriting turns one printer's toolpaths into another's.

So Crossprint carries the recipe across and deliberately discards the cached slice. Open the converted file and press Slice; the target's slicer produces its own G-code from your settings.

What comes across, and what doesn't

Carried over

  • All model geometry, untouched
  • Object positions, re-placed onto the target's bed
  • Multi-plate layout
  • Filament colours, types and slot order
  • Per-triangle colour painting
  • Support and seam painting
  • Your print settings — layer height, walls, infill, speeds — marked as deviations so the slicer honours them instead of its own defaults
  • Variable layer-height profiles, clamped into the target's nozzle range
  • Modifiers and per-object settings that both slicers define

Not carried over

  • Cached toolpaths and G-code — by design, see above
  • Settings the target's slicer has no definition for
  • Machine settings: nozzle variants, per-extruder kinematics, AMS routing, purge matrices. The slicer fills these from its own presets, which is what makes the file load at all
  • Custom filament preset definitions — each filament is re-pointed at a real preset the target actually ships
  • Nozzle sizes other than 0.4 mm: every target is the 0.4 mm profile

Supported printers, and how far each is verified

Verified means the output was checked field-by-field against a real project file saved by that printer's own slicer, and opened in that slicer to confirm geometry, colours and print recipe survived. Best-effort means the same mechanism, applied to a model in the same hardware class, with no real sample to check against. Best-effort conversions work — they are just worth opening and eyeballing before you commit filament to them.

Running it yourself

The hosted converter has upload limits and a queue. The same code runs locally with neither, and your files never leave your machine:

git clone https://github.com/ELI7F/crossprint
cd crossprint
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
./run_web.ps1

There is a command line too, including a dry run that reports what would change without writing anything:

python cli.py convert project.3mf --to h2d --report
python cli.py convert project.3mf --to u1 --dry-run --json
python cli.py models

Frequently asked questions

Will my colour painting survive?

Yes. Per-triangle paint is stored as a packed encoding referencing colour slots, and Crossprint remaps those slots along with the filament list, so painted facets keep pointing at the colour you painted them. If the target ends up with fewer slots than a painted facet references, that is reported under Colour painting rather than silently changing your artwork.

The converted file opens but all my print settings are back to defaults.

That is the failure mode this tool was largely built to eliminate, so first check the change list for Print profile — it names how many of your settings were marked as deviations. Zero there means the target's print preset wasn't found and the slicer fell back to its own values; the report says so explicitly.

If the count is healthy and the settings are still wrong, that is a bug worth reporting — include the source file if you can.

My slicer says "invalid configuration file" or shows no geometry.

Those two messages usually have the same cause: the config load threw partway through, so the model was never read. It means a setting value the target can't parse got through. Please open an issue with the source file and the target you picked — every instance of this so far has been a specific, fixable disagreement between the two slicer forks.

Check first that you're running a current version of the target's slicer. The vocabulary Crossprint filters against comes from recent builds, and a much older slicer may not define settings that are perfectly valid today.

What happens with more colours than the target can hold?

On a Snapmaker U1 the answer is nothing special: four toolheads are mounted at once, but the total colour count per print isn't capped — beyond four the printer prompts you to swap spools, and that needs no extra data in the file.

On Bambu targets with an enforced capacity, conversion stops with an error naming the numbers instead of merging colours for you. Silently deciding which two of your colours become one would change your model without asking.

Can I convert a .gcode.3mf or a plain STL?

No. A .gcode.3mf is sliced output with no editable project inside, and an STL has no print recipe to carry over — there would be nothing to convert. Crossprint needs a project file saved from the slicer (in Bambu Studio and Snapmaker Orca: File → Save Project As).

Why does my object land somewhere else on the plate?

It shouldn't — it should land in the same relative spot on a differently sized bed. Object positions in a 3MF are absolute coordinates in a world laid out as a grid of plates spaced from the source printer's bed size. Converting without touching them puts an 11-plate small-bed project entirely outside a large printer's printable area. Crossprint re-places each object using the slicer's own layout rule, keeping it on the plate you put it on, and reports how many objects it moved.

Does it work with a 0.2, 0.6 or 0.8 mm nozzle?

It converts, but every target is the 0.4 mm profile. If your source project was sliced for a different nozzle, the change list says so under Check before printing: your line widths and flow come across as you set them, onto a profile built around a nozzle they weren't chosen for. Review those before printing.

Is it free? What's the licence?

Free, and open source under AGPL-3.0 — including commercial use, provided you publish your changes if you host a modified copy. The source is on GitHub. The AGPL follows from the vendored printer presets, which come from BambuStudio and Snapmaker Orca.

Something converted badly. What's useful in a bug report?

The source .3mf, the target you picked, the change list (the CLI's --json gives it in full), and what the slicer did that it shouldn't have. If you can, also save the same project from the target's slicer with Save Project As — a correct file for the same models is the single most useful thing for diffing against.
